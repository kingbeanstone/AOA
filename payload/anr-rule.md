# /anr — Android ANR 덤프 분석

사용자가 `/anr <덤프파일경로>` 형식으로 호출했다.
사용자 메시지에서 덤프 파일 경로를 식별해 파서를 실행하고 분석한다.
경로가 비어 있으면 사용자에게 덤프 파일 경로를 요청하고 중단한다.

* 필요한 파서: `anr_parse.py` v1.21 이상
* 파서 위치:
  * Linux/macOS/WSL: `$HOME/.anr-tool/anr_parse.py`
  * Windows: `%USERPROFILE%\.anr-tool\anr_parse.py`

═══════════════════════════════════════════════════════════════
1. 절대 규칙
═══════════════════════════════════════════════════════════════

1. **원본 덤프 파일을 절대 직접 읽지 말 것.**
   덤프는 수십~수백 MB라 직접 읽으면 컨텍스트가 폭주해 분석 불가.

2. **`_anr_parsed.txt` 만 읽고 분석한다.**
   파서는 분석용 파일(`_anr_parsed.txt`)과 참고용 부록 파일
   (`_anr_crashes.txt`)을 동시에 생성한다. 분석은 전자만 사용한다.

3. **`_anr_crashes.txt` 는 읽지 않는다.**
   이 파일은 사용자가 직접 참고하기 위한 raw dump 이며,
   ANR 분석에는 사용하지 않는다. 보고서에는 파일 경로만 안내한다.

4. **`anr_parse.py` 경로는 OS와 셸에 따라 달라진다. (2절 참고)**

5. **작업 전 반드시 셸 환경을 먼저 확인하고 경로·명령을 결정한다.**

6. **표면 증상에서 멈추지 말 것.** (5절 참고)
   "메인 스레드가 X에서 Waiting" 은 증상일 뿐 원인이 아니다.
   **왜 그 대기가 풀리지 않았는지**까지 추적해야 한다.

7. **로그 라인 끝의 ` … (+N자 절단)` 표시는 파서가 절약을 위해
   라인을 잘랐다는 뜻이다.** 절단된 부분은 보통 객체 dump 의
   세부 필드라 분석에 영향이 없다. 잘린 정보를 추정해서 채우지 말 것.

8. **`[5]` 헤더의 "노이즈 태그 N건 필터링됨" 표시는 파서가
   ANR 분석과 무관한 시스템 로그(SurfaceFlinger, Insets 등)를
   사전에 제거했다는 뜻이다.** 누락된 태그가 있어도 의도된 동작이며,
   "관련 로그가 없다"는 표현은 사용하지 말 것. 대신 `[5]` 에 남아 있는
   로그만으로 추론한다.

2. 셸 환경 감지 및 경로·명령 결정 (필수 — 작업 전 1회 수행)

### 2-1. 감지 명령

```
echo $PSVersionTable
```

- 출력 비어 있음/오류 → bash / zsh / CMD
- `PSVersionTable` 출력 → PowerShell

bash/CMD 구분이 필요한 경우: `echo $SHELL`

### 2-2. 환경별 경로 및 Python 호출

| 환경 | 스크립트 경로 | Python 실행 순서 |
|------|-------------|------------------|
| **PowerShell** | `"$env:USERPROFILE\.anr-tool\anr_parse.py"` | `py` → `python` → `python3` |
| **CMD** | `"%USERPROFILE%\.anr-tool\anr_parse.py"` | `py` → `python` → `python3` |
| **bash / zsh** | `"$HOME/.anr-tool/anr_parse.py"` | `python3` → `python` |

### 2-3. 실행 예시

**PowerShell:**
```powershell
py "$env:USERPROFILE\.anr-tool\anr_parse.py" "<덤프경로>"
```
**CMD:**
```cmd
py "%USERPROFILE%\.anr-tool\anr_parse.py" "<덤프경로>"
```
**bash / zsh:**
```bash
python3 "$HOME/.anr-tool/anr_parse.py" "<덤프경로>"
```

### 2-4. Python 실행 실패 시

`py` → `python` → `python3` 순으로 재시도. 모두 실패 시 사용자에게
Python 설치 여부 확인 후 중단. 스크립트 파일 자체가 없으면(`No such file`)
설치 스크립트가 실행되지 않은 것이므로 사용자에게 안내하고 중단.

### 2. 함수 콜 스택 (Trace)

**출처: 파싱 결과 `[3]` 전용.**

- `[3]` 이 `(VM TRACES AT LAST ANR 섹션 없음)` 이면:

### 3. 서술 항목 (본질 추적)

이 섹션은 `_anr_parsed.txt` 의 내용만 사용해서 작성한다.

- **타임라인 요약**: 사건 발생 순서.
- **직접 트리거**: 메인 스레드를 막은 호출 (파일:라인). 표면 증상.
- **블로킹이 풀리지 않은 이유** (5절 체크리스트 결과):
  - 대기 대상이 무엇인가
  - 누가 해제해야 하는가
  - 왜 해제되지 못했는가
- **근본 원인**: 구조적 결함으로 기술. 확신도(상/중/하)를 함께 표기 (5-7).
- **대안 가설**: 차순위 후보가 있으면 한 줄로 남긴다 (없으면 생략).
- **근거**: 파싱 결과의 어느 섹션·라인이 근거인지 인용.
  인용 형식 예시:
  - `[3] VM TRACES`: <스레드명> 상태 <상태값>, <라인 위치>
  - `[4] logcat`: HH:MM:SS <태그> <메시지 요약>
  - `am_anr`: <필드 값>
- **해결 방안**: 근본 원인에 대응하는 구조적 수정안.
  일반론("메인 스레드 막지 마세요")만으로는 부족하다.

### 4. 부록 안내 (마지막 줄)

보고서의 가장 마지막에 다음 한 줄만 추가한다:

```
> Crash 기록(참고용)은 별도 파일 `<원본>_anr_crashes.txt` 에서 확인 가능합니다.
```

이게 전부다. Crash 내용 요약, 해석, 평가, ANR 관련성 언급은 작성하지 않는다.

═══════════════════════════════════════════════════════════════
5. 근본 원인 추적 체크리스트 (필수)
═══════════════════════════════════════════════════════════════

보고서 작성 전 반드시 아래 단계를 수행한다.

### 5-0. 진단 우선순위 (판단 순서)

input dispatch 계열 ANR 디버깅의 표준 순서를 따른다. **위에서부터** 확인해
가장 먼저 성립하는 가설을 1순위 후보로 삼되, 아래 단계도 끝까지 점검해
교차 증거를 모은다 (한 단계에서 멈추지 말 것 — 1절 6번).

| 단계 | 무엇을 보는가 | 근거 섹션 | 세부 |
|------|-------------|----------|------|
| 1. ANR 유형 | Input / Broadcast / Service / Provider | `am_anr`, `[2]` | — |
| 2. 메인 스레드 상태 | Waiting/Blocked/Native/GC/Runnable | `[3]` | 5-1 |
| 3. 데드락 / 락 / Binder | 락 보유·순환 대기·원격 응답 지연 | `[3]` | 5-2, 5-3 |
| 4. 그래픽 파이프라인 | GPU 과점, BufferQueue 폭증, 렌더 지연 | `[4] Render`, `-k` | 5-6 |
| 5. 크로스 프로세스 의존 | system_server·원격 프로세스 대기 | `[3]`, `[5]` | 5-2 |
| 6. 일반 slow path | I/O, sleep, CPU 집약 | `[3]`, `[4]` | 5-4, 5-5 |
| 7. 근거 점수화 | 후보별 증거 강도 평가 | 위 전부 | 5-7 |

> **중요:** 이 판단은 전부 LLM(분석자)이 수행한다. 파서는 점수를 매기지 않으며,
> 점수 표시를 출력에 넣지 않는다. 파서 출력은 가공 없는 추출 결과다.

### 5-1. 메인 스레드 상태 분류

`[3]` 의 main 스레드 상태에 따라 분기:

| 상태 | 다음 단계 |
|------|----------|
| `Waiting` (object 명시) | 5-2 |
| `Blocked` (waiting to lock) | 5-3 |
| `Native` / `Sleeping` | 5-4 |
| `WaitingForGcToComplete` / `WaitingPerformingGc` | 5-5 (GC 분기) |
| `Runnable` | 5-5 (CPU 분기) |

### 5-2. 동기화 객체 대기 — 해제 책임자 추적

| 대기 대상 | 해제 호출 | 해제 주체 |
|----------|----------|----------|
| `CountDownLatch` | `countDown()` | 다른 스레드/콜백 |
| `Semaphore` | `release()` | 다른 스레드 |
| `Future` | `complete()` / 작업 완료 | 워커 |
| `Condition.await()` | `signal()` / `signalAll()` | 다른 스레드 |
| `Object.wait()` | `notify()` / `notifyAll()` | 다른 스레드 |
| `ReentrantLock.lock()` | 보유 스레드의 `unlock()` | 보유 스레드 |
| Binder transact | 원격 응답 | 원격 프로세스 |

**핵심 질문:** 해제 주체가 실행될 수 있는 환경인가?

**데드락 패턴 의심:**
- 메인 스레드 대기 → 해제는 메인 스레드 메시지 큐 콜백
  (`ServiceConnection.onServiceConnected`, `BroadcastReceiver.onReceive`,
  `Handler.post`, `runOnUiThread`, RxJava `AndroidSchedulers.mainThread()`,
  Coroutine `Dispatchers.Main`)
- `bindService` + `await`
- `runBlocking { withContext(Dispatchers.Main) { ... } }` on main

### 5-3. 락 경합 / 락 데드락

- 락을 쥔 스레드(`held by tid=N`)의 콜 스택을 함께 확인.
- 그 스레드가 **다른 락을 기다리고 있다면 → 락 데드락 의심.**
  양방향 관계 확인:
  - A: holds L1, waiting for L2
  - B: holds L2, waiting for L1
  → 순환 대기 성립 시 데드락 확정.
- 락 보유 스레드가 다른 작업(I/O, GC, sleep) 중이라면 → 단순 락 보유 지연.
- **참고:** `[5]` 에 `system_server: Long monitor contention with owner ...`
  로그가 있으면 Android 가 자체적으로 감지한 락 경합 정보 — 분석 보조 단서.

### 5-4. Native / Sleeping

- JNI 호출, 동기 파일/네트워크 I/O, `Thread.sleep` 등.
- StrictMode 위반 가능성.

### 5-5. GC / Runnable

**GC 분기** (`WaitingForGcToComplete` / `WaitingPerformingGc`):
- 다른 스레드들의 할당 패턴 확인 (워커가 무한 할당 중인가?).
- `[4] logcat` 의 `Background concurrent ... GC freed ...` 빈도 확인.
- 할당 속도 > 회수 속도 → GC Thrashing.
- 메인 스레드 자체도 할당 루프에 참여하는지 확인.
- 근거 인용 시 `[3]`, `[4]` 만 사용. 메모리 관련 crash 추정은 금지
  (crash 파일은 본 분석에서 사용하지 않음).
- 용어 정확성: catch 되어 `clear()` 되는 명시적 할당 폭주는
  **메모리 leak 이 아니다**. "leak" 대신 "할당 폭주", "GC Thrashing",
  "가용 메모리 고갈" 같은 정확한 표현을 쓸 것.
- 해결 방안의 본질: "최적화" 가 아니라 "이 할당 루프 자체가 잘못된 설계"
  라는 점을 짚을 것. 무한 루프 안에서 메가바이트급 할당이 발생하는
  코드는 정상적 비즈니스 로직일 수 없음.

**Runnable 분기**:
- 메인 스레드 CPU 집약 작업 (큰 JSON, 이미지 디코딩, 큰 루프).

### 5-6. 그래픽 파이프라인 (단계 4)

메인 스레드가 명확한 락/대기에 걸려 있지 않은데 ANR 이 났거나,
다른 앱(wallpaper, 게임 등)이 GPU 를 과점한 정황이 의심될 때 확인한다.

- `[4] Render` 의 `SurfaceFlinger` / `BufferQueue` / `HWUI Davey!` 빈도.
  특히 `Davey! duration=...ms` 는 UI 스레드 프레임이 그만큼 멈췄다는 직접 증거.
- 파서는 그래픽 파이프라인 폭증을 **부하 요약**으로 접어 보여준다
  (`총 N건`, 태그별 건수, `frameNumber A→B (+증가량)`). 개별 프레임 줄이 아니라
  이 요약으로 부하 규모를 판단한다.
- **frameNumber 추이 해석:** 한 컴포넌트(특히 wallpaper)의 frameNumber 가
  ANR 구간 내내 꾸준히 큰 폭(+수백~수천)으로 증가했다면, 그 시간 동안
  프레임 생산/합성이 쉬지 않고 일어났다는 뜻 — GPU 를 지속 점유한 정황이다.
  단, 증가 자체가 곧 원인은 아니므로 메인 스레드 상태(5-1)·Davey!·avgGpuLoad
  와 교차로 확인한다.

- **GPU 경쟁을 "단순 기여요인" 으로 과소평가하지 말 것.** 메인 스레드가 락/HAL
  대기로 보이더라도, 아래가 동시에 성립하면 GPU 경쟁이 그 대기를 만든
  **공동 근본 원인(또는 1순위 원인)** 일 수 있다. 락 구조만 원인으로 단정 금지:
  - frameNumber 가 ANR 구간 내내 큰 폭(+수천 이상)으로 끊김 없이 증가, **그리고**
  - `avgGpuLoad` 가 포화 수준(90+ 등) 지속, **그리고**
  - 락/HAL 을 쥔 스레드(해제 책임자)가 렌더·합성·GPU·DVFS 경로에서 지연됨.
  → 이 경우 "메인 스레드가 동기 대기한 구조" 와 "GPU 포화로 해제 주체가 늦어진 것"
    중 **무엇이 없었으면 ANR 이 안 났는가** 를 따진다. GPU 포화가 없으면 대기가
    정상 시간 내 풀렸을 정황이면, GPU 경쟁을 근본 원인으로 올린다.
- 확신도 표기 시, 강한 GPU 신호(frameNumber 지속 증가 + avgGpuLoad 포화)를
  근거로 가진 가설을 약한 정황으로 깎아내리지 않는다. 신호가 강하면 강하게 적는다.
- 같은 단말의 다른 프로세스(특히 wallpaper)가 GPU 를 점유하면 본 앱의
  렌더가 밀려 input dispatch 가 지연될 수 있다.
- **ANR 이후 GPU 지속 여부:** `[4] Render` 는 ANR 이후 구간(+120s)까지 본다.
  ANR 이후로도 그래픽 폭증·`avgGpuLoad` 포화·`Davey!` 가 계속되면, 이 GPU 부하가
  일시적 튐이 아니라 **구조적 포화**였다는 방증이다. 단 ANR 이후 상태는 원인의
  직접 증거가 아니라 보강 정황이다 — 원인 판단의 핵심 근거는 ANR 이전 구간
  (frameNumber 증가 추이, avgGpuLoad)에서 가져온다.
- **써멀 스로틀링 단서:** `SIOP_GPU_FREQ_MAX`, `GPUMaxFreq`, `GPUFreqMax`,
  `HYPER-HAL`/`SemDvfsHyPerManager` 의 GPU 클럭 상한 설정이 ANR 구간에 보이면,
  발열 때문에 GPU(또는 CPU) 주파수에 상한이 걸려 성능이 강제로 낮아진 상태다.
  GPU 부하 포화(avgGpuLoad)와 겹치면 "부하는 높은데 클럭은 제한" → 렌더/합성
  지연이 가중되는 전형적 패턴이므로, GPU 경쟁 가설의 강한 보강 근거로 쓴다.
- 정황이 보이면 **6절 키워드 2차 분석**으로 검증:
  `-k wallpaper`, `-k BLASTBufferQueue`, `-k SurfaceFlinger` 등.
  (1차 `[5]` 는 ANR 패키지만 보므로 GPU 경쟁 상대는 2차로 봐야 드러남.)
- 단, 그래픽 로그가 많다는 것만으로 원인 단정 금지. 메인 스레드 상태(5-1)와
  교차 검증해 "렌더 지연이 실제로 메인 스레드를 막았는지" 인과를 확인한다.

### 5-7. 근거 점수화 (단계 7)

위 단계에서 나온 후보 원인이 둘 이상이거나 단일 후보의 확신이 낮을 때,
각 후보의 증거 강도를 평가해 보고서의 "근본 원인" 확신도를 정한다.
**이 점수는 분석자(LLM)가 매기며, 파서 출력에는 점수가 없다.**

후보별로 아래를 따져 상/중/하로 표기:

- **직접성**: 메인 스레드를 막은 호출과 직접 연결되는가, 정황 증거인가.
- **시간 일치**: 해당 로그/상태의 시각이 ANR 지연 구간과 겹치는가.
- **교차 일치**: `[3]`(스택) · `[4]`(logcat) · `[5]`(패키지 로그) 중
  둘 이상이 같은 결론을 가리키는가.
- **대안 배제**: 다른 단계(2~6)의 가설이 증거로 배제되는가.
- **인과 역전 점검**: 메인 스레드를 막은 직접 호출(증상)과, 그 대기를 풀어주지
  못하게 만든 배경 원인(예: GPU 포화로 해제 주체 지연)을 구분한다. 직접성이
  높다고 자동으로 1순위가 아니다 — 배경 원인이 없었으면 ANR 이 안 났을 정황이면
  배경 원인의 점수를 직접 증상보다 높게 줄 수 있다. 강한 GPU 신호(frameNumber
  지속 증가 + avgGpuLoad 포화)는 "정황" 이 아니라 강한 증거로 취급한다.

보고서 3절 "근본 원인" 에는 가장 점수가 높은 후보를 본문으로, 차순위
후보는 "대안 가설" 로 한 줄 남긴다. 확신도(상/중/하)와 그 근거를 함께 적는다.
증거가 약하면 약하다고 명시하고, 단정하지 않는다.

### 6-1. 키워드 모드 재파싱

`anr_parse.py` 에 `-k <키워드>` 를 붙여 다시 실행한다. **1차 분석과 동일한 처리**
(ANR-300s ~ ANR 시간 윈도우, 노이즈 태그 필터, 연속 동일 태그 압축, 라인 절단)를
적용하되 **매칭 조건만 키워드로 교체**한다 (1차는 ANR 패키지명, 2차는 사용자 키워드).
키워드는 대소문자 무시, 복수 키워드는 OR 매칭.

> 1차는 ANR 난 프로세스 기준, 2차는 사용자가 의심하는 관련 프로세스/모듈 기준.
> 따라서 1차의 노이즈 필터가 동일하게 적용된다. 노이즈 필터에 걸리는 태그
> 자체를 보고 싶다면 그 태그를 키워드로 지정한다 (예: `-k BLASTBufferQueue`).

**PowerShell:**
```powershell
py "$env:USERPROFILE\.anr-tool\anr_parse.py" "<덤프경로>" -k <키워드>
```
**CMD:**
```cmd
py "%USERPROFILE%\.anr-tool\anr_parse.py" "<덤프경로>" -k <키워드>
```
**bash / zsh:**
```bash
python3 "$HOME/.anr-tool/anr_parse.py" "<덤프경로>" -k <키워드>
```

- **복수 키워드:** `-k <키워드1> -k <키워드2>` (하나라도 포함되면 매칭)

### 6-2. 결과 읽기 및 보고서

- 생성된 `<원본>_anr_keyword_<키워드>.txt` **만** 읽고 분석한다.
  (원본 덤프 직접 읽기 금지 — 1절 절대 규칙 동일하게 적용)
- 1차 결과(`_anr_parsed.txt`)와 1차 보고서(`_anr_analysis.md`)는
  **덮어쓰지 않는다.**
- 2차 보고서는 `<원본>_anr_analysis_<키워드>.md` 로 저장한다 (이력 보존).
- 키워드 결과가 비어 있으면("매칭 라인 없음") 추정으로 채우지 말고
  "해당 키워드의 로그가 분석 범위(ANR-300s ~ ANR) 내에 없음"을 그대로 보고한다.
  (단, 노이즈 필터로 제거됐을 수 있으므로 "존재하지 않는다"고 단정하지 말 것.)
